# v1.4 Kernel Checkpoint

## Purpose

This document is the synchronization point between the approved v1.4 architecture and the actual repository state.

## Recovered implementation sequence

1. Foundation and architecture contract
2. Identity resolution and global deduplication
3. Canonical Search contract
4. Discovery and qualification gating
5. Transactional persistence boundary
6. Intelligence/provider gateway
7. AI gateway
8. MAX adapter contract
9. Commercial Action → Order → Economics
10. API/PWA/Android surface and integration hardening

## Current state

### 1. Foundation and architecture contract — implemented

The modular-monolith boundary, dependency direction, critical invariants, operational controls and quality gates are represented in code and the machine-readable architecture contract.

### 2. Identity — implemented

Global identity resolution uses INN as the primary Russian B2B cross-source deduplication key. Ambiguous or incomplete identity data is quarantined or sent to review.

### 3. Search — implemented

Canonical search validates region, industry, identifiers, duplicate keys and selection level before results enter application workflows.

### 4. Discovery and qualification — implemented

Search output is separated from canonical Identity. Qualification is conservative: unresolved identity, weak evidence, missing contact or unconfirmed economic fit remains in review.

### 5. Transactional persistence — implemented and hardened

PostgreSQL is the transactional authority.

The platform now has persistence adapters for:

- Identity
- Search Candidate
- Evidence
- Audit
- Idempotency
- Outbox
- Quarantine

Audit execution context is persisted through the forward-only 0003_audit_context.sql migration.

The outbox adapter shares the caller transaction and therefore preserves the required state-change/outbox atomicity boundary.

### 6. Intelligence/provider gateway — implemented

Research budgets, provider capability checks, R1-R4 source routing, provider waterfall selection, source references and usage limits are enforced at the gateway. The Intelligence application service materializes routed provider claims as traceable Evidence and has a PostgreSQL integration test.

The remaining work in this contour is composition into Qualification.

### 7. AI gateway — implemented at execution boundary

AI execution is isolated behind an application gateway with explicit authorization, policy, evidence validation, execution budgets, model/prompt version checks, provider-result validation and append-only audit emission.

Durable AI run persistence and concrete model-provider adapters remain pending. The domain/application contract remains provider-neutral.

### 8. MAX adapter — contract implemented

MAX is isolated as an adapter with canonical inbound event normalization and idempotent outbound communication.

Real MAX transport/webhook integration remains outside the domain core.

### 9. Commercial Action → Order → Economics — domain contract implemented

Critical commercial action is identity-, permission-, policy- and evidence-gated. Order lifecycle and economic lineage are represented as domain contracts with tests.

Durable persistence and end-to-end order execution are still pending.

### 10. API/PWA/Android — not started

Client surfaces remain deliberately downstream of the canonical application/domain contract.

## Quality gate

A stage is considered complete only when its contract, invariants, failure modes, tests and observability are represented.

The current branch is v1.4-kernel-hardening, based directly on the approved v1.4-foundation checkpoint.

No Airtable, Replit or Bitrix24 implementation is part of the v1.4 core.
