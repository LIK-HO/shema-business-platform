# v1.4 Kernel Checkpoint

## Purpose

This document is the synchronization point between the approved v1.4 architecture and the actual repository state.

## Approved 12-element kernel

The approved working decomposition of the v1.4 kernel is:

1. Foundation / Architecture Contract
2. Identity
3. Canonical Search
4. Discovery + Qualification
5. Transactional Persistence
6. Intelligence / Research
7. AI Gateway
8. MAX / Communication Adapter
9. Commercial Action
10. Order
11. Economics
12. Canonical API / Experience Boundary

The ten-stage architecture sequence below groups Order and Economics together for architectural reporting; the kernel workstream tracks them as separate elements 09-11 and keeps the API/experience boundary as element 12.

## Current state

### 1. Foundation and architecture contract — implemented

The modular-monolith boundary, dependency direction, critical invariants, operational controls and quality gates are represented in code and the machine-readable architecture contract.

### 2. Identity — implemented

Global identity resolution uses INN as the primary Russian B2B cross-source deduplication key. Ambiguous or incomplete identity data is quarantined or sent to review.

### 3. Search — implemented

Canonical search validates region, industry, identifiers, duplicate keys and selection level before results enter application workflows.

### 4. Discovery and qualification — implemented

Search output is separated from canonical Identity. Qualification is conservative: unresolved identity, weak evidence, missing contact or unconfirmed economic fit remains in review.

### 5. Transactional persistence — implemented and hardened

PostgreSQL is the transactional authority.

The platform now has persistence adapters for:

- Identity
- Search Candidate
- Evidence
- Audit
- Idempotency
- Outbox
- Quarantine
- Commercial Action
- Order
- Economic Entry
- AI Run

Audit execution context is persisted through the forward-only 0003_audit_context.sql migration.

The outbox adapter shares the caller transaction and therefore preserves the required state-change/outbox atomicity boundary.

### 6. Intelligence/provider gateway — implemented

Research budgets, provider capability checks, R1-R4 source routing, provider waterfall selection, source references and usage limits are enforced at the gateway. The Intelligence application service materializes routed provider claims as traceable Evidence and has a PostgreSQL integration test.

The Intelligence service materializes routed provider claims as persisted Evidence. Qualification remains an explicit downstream gate and consumes trusted evidence state; provider execution does not bypass Qualification. Direct end-to-end composition remains at the application boundary.

### 7. AI gateway — execution and persistence implemented

AI execution is isolated behind an application gateway with explicit authorization, policy, evidence validation, execution budgets, model/prompt version checks, provider-result validation, durable PostgreSQL run persistence and append-only audit emission.

Concrete external model-provider adapters remain outside the core contract and can be added without changing domain semantics.

### 8. MAX adapter — contract implemented

MAX is isolated as an adapter with canonical inbound event normalization and idempotent outbound communication.

Real MAX transport/webhook integration remains outside the domain core.

### 9. Commercial Action → Order → Economics — execution and persistence implemented in core

Commercial Action is identity-, permission-, policy- and evidence-gated. External communication is blocked unless the action is READY; Order creation is blocked unless the action is SENT or COMPLETED. PostgreSQL persistence now covers commercial actions, order headers/lines and append-only economic entries with source lineage.

End-to-end orchestration around real external transport and production settlement remains outside this core checkpoint.

### 10. API/PWA/Android — canonical API contract established

The canonical HTTP boundary is recorded in `api/openapi.yaml` and `docs/API_CONTRACT.md`. Web, PWA and Android are constrained to the same commands, queries, authorization/policy gates, idempotency model, correlation context and error envelope. UI implementation and runtime IAM integration remain downstream.

## Quality gate

A stage is considered complete only when its contract, invariants, failure modes, tests and observability are represented.

The current branch is v1.4-kernel-hardening, based directly on the approved v1.4-foundation checkpoint.

No Airtable, Replit or Bitrix24 implementation is part of the v1.4 core.
