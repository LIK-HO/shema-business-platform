# v1.5 Runtime Core

## Purpose

v1.5 begins productization of the already frozen kernel without changing domain semantics.

The first runtime increment is provider-neutral production authentication:
- Bearer JWT is accepted only through the Authorization header.
- Signature verification uses a configured JWKS endpoint.
- issuer, audience, subject and expiration are mandatory.
- supported signing algorithms are explicitly allow-listed.
- JWKS access uses bounded timeout and key-set caching.
- invalid authentication fails closed.
- authentication only establishes actor identity and an optional trust level.
- RBAC authorization and business policy remain separate gates.

## Security boundary

The JWT adapter belongs to adapters/ and implements the foundation AuthenticationPort. The domain and application layers do not import JWT, PyJWT, JWKS or provider SDKs.

No token, signing key or provider secret is persisted in business data or emitted into audit/application error responses.

The HTTP edge returns 401 with WWW-Authenticate: Bearer when authentication credentials are absent or invalid.

## Provider neutrality

The adapter is configured with:
- issuer URL;
- audience;
- JWKS URL;
- allowed asymmetric/JWKS signing algorithms;
- small clock-skew leeway;
- optional claim name for trust-level mapping.

A concrete IAM provider is deployment configuration, not a domain dependency.

## Next v1.5 sequence

1. JWT/JWKS authentication boundary — implemented.
2. Authorization policy materialization — bind IAM claims/groups/scopes to explicit permissions without moving authorization into the token parser.
3. Production observability — structured logs, metrics and trace propagation around commands/jobs/outbox.
4. Recovery and security drills — key rotation and database rollback are now executable gates; lease reclaim and outbox replay are already covered by durable execution integration tests.
5. Concrete MAX and intelligence adapters — provider-specific transport outside the domain core.
6. Controlled deployment boundary — environment/configuration promotion and rollback.
7. Web/PWA/Android clients — only after runtime contracts are stable.

The v1.5 core is complete only when these runtime boundaries are validated by CI, integration/security tests and controlled recovery checks.


## Observability boundary

Structured telemetry is now a non-authoritative runtime layer:
- HTTP request completion/failure events carry correlation and actor context without request credentials or bodies.
- Durable job claim, lease renewal, completion and failure/retry events are emitted outside the business-state transaction.
- Outbox claim, publication and publisher-failure events are emitted outside the business-state transaction.
- Sensitive telemetry attributes are recursively redacted.
- A telemetry sink failure is swallowed and cannot alter business state, retries, leases, publication or audit semantics.

## Current v1.5 sequence

1. JWT/JWKS authentication boundary — implemented and CI-validated.
2. Structured observability framework + HTTP/job/outbox instrumentation — implemented and CI-validated.
3. Authorization policy materialization — implemented: verified IAM roles/scopes are converted to explicit application permissions by a separate RBAC materializer; the JWT verifier itself never grants business permissions.
4. Recovery and security drills — key rotation, database recovery, lease reclaim and outbox replay.
5. Concrete MAX and intelligence adapters — provider-specific boundaries remain outside the domain core.
6. Controlled deployment boundary — configuration promotion and rollback.
7. Web/PWA/Android clients — downstream of the stable runtime core.

The v1.5 core is not considered frozen until authorization, recovery/security checks and controlled-release invariants have their own executable tests and green CI boundaries.


## Authorization materialization boundary

The verified JWT adapter may expose normalized IAM attributes needed by authorization (roles, scopes). It does not decide application permissions. AuthorizationMaterializer maps those attributes to explicit Permission values, and the HTTP edge places only the resulting permission set into RequestContext. Business services continue to enforce permission, policy and evidence gates independently.
