# СХЕМА Business Platform — v1.5 Core Maturity

## Authoritative core

The mature core is the smallest boundary that owns business truth and remains correct when external systems fail:

- `domain/` — business invariants and state transitions;
- `foundation/` — authorization, policy, evidence, idempotency, audit, recovery and outbox contracts;
- `application/` — commands, workflows and orchestration;
- `platform/postgres*` — transactional persistence authority;
- durable jobs, leases, bounded retry and outbox delivery;
- canonical API semantics and error contracts.

## External boundary

These remain deliberately outside business truth:

- concrete OIDC/IAM providers;
- MAX/Telegram/Email transport implementations;
- concrete intelligence providers;
- concrete AI model providers;
- Web/PWA/Android UI;
- payment/settlement provider integrations;
- Airtable, Replit and Bitrix24.

They may fail, timeout, duplicate requests or disappear without being allowed to corrupt canonical state.

## Maturity gates

Core maturity requires all seven gates:

1. Correctness — invalid domain state is rejected.
2. Atomicity — required business state, idempotency, audit and outbox changes commit together.
3. Concurrency — competing workers cannot bypass state ownership or leases.
4. Recovery — crashes, lease expiry and retryable failures converge to a recoverable state.
5. Security — authorization, policy and evidence gates fail closed.
6. Observability — correlation, audit and safe diagnostics explain failure without leaking secrets.
7. Release safety — migrations, code quality, integration tests and dependency/security checks are deterministic release gates.

## Fault model

The core is explicitly hardened against:

- worker crash before completion;
- worker crash after an external send/publication;
- duplicate delivery or retry;
- lease expiry during execution;
- database rollback;
- concurrent critical commands;
- dependency timeout/unavailability;
- concurrent deployment;
- edited historical migration.

## Database ownership safety

Lease/state ownership is enforced in PostgreSQL as well as in the repository layer. A persisted job, outbox delivery or commercial send cannot hold a partial lease or a lease in a non-owning state. Invalid combinations fail at the storage boundary and therefore cannot be created by a future adapter or recovery script accidentally.

## Migration safety

Schema migration is a core platform concern. The migration runner:

- serializes deployers with a transaction-scoped PostgreSQL advisory lock;
- records immutable migration checksums;
- rejects modified historical migrations;
- applies one ordered migration plan in a single transaction;
- refuses gaps in migration numbering;
- migration 0009 installs database-level state/lease ownership constraints.

## Completion boundary

Core maturity does not require every external provider to be integrated. It requires every external effect to have a safe adapter contract while PostgreSQL remains authoritative and recoverable.
